# Logical checklist

The starting checklist for the logical design: what the board does, for whom, in which states, and at what cost. Apply it at the logical design stage (ST4) and in the logical part of every schematic review (ST6). The electrical checklist is `references/checklist-electrical.md`, the board checklist `references/checklist-board.md`, and the board-type packs `references/packs.md`.

## How to use it

- Pin assignment is item one of every review. Start with LG-00, then EL-01 in the electrical checklist; at the board, BD-01.
- Apply every item. Give each a result in your report: met, not met, does not apply (with the reason), or cannot tell (with what would tell). A brief that names only some items does not shorten the list; apply all of it and say so under Deviations.
- **What to check** names the area and the question. It never gives the answer.
- **Authority** is where the answer comes from. "Datasheet" always means this part's own datasheet, read now, with the documents it delegates to. A standard or regulation is fetched and cited; never quote one from memory (WR-01). If the authority is silent, follow WR-20.
- **Stage** is when the item is normally applied (the coordinator's ST numbers). An item can be applied again at any later stage.
- **Script** names a script and sub-command that helps, by bare name. A review list is evidence for you to close with reasons, not a pass. "none" means the item is judged by a reviewer, with evidence.
- **Switch** says when the item applies. "always" means every board; mark it "does not apply" with a reason if the board has nothing it covers. "always; more under X" means the item always applies and the board-type switch X adds weight to it. A switch name alone means the item applies only when that switch is on. Switch names are listed in `references/packs.md` (Board-type switches).
- Use the project's copy in `design/checklists/logical.md`. It may have grown.

## Living document: adding and retiring items

- **Adding.** Anyone may propose an item: a worker in report section 12, a reviewer, or the user. A proposal has all six fields. The coordinator puts it to the user. An accepted item goes into the project's copy with the next free number in this list, and keeps that ID for good. An item that looks useful for every board may be offered to the user as feedback for the skills; it is never sent automatically. In the skill's own copy, a new item also takes the next free ID.
- **Retiring.** An item is never deleted and its ID is never reused, so old reports still resolve. To retire one, keep the row and start its "What to check" cell with "Retired <date>: <reason>; see <new ID>". Retire an item only when another item covers all of it, or its authority no longer exists. In a project copy, the user decides. An item that does not fit one board is not retired; it is marked "does not apply" with a reason in that review.

## Requirements and scope

| ID | What to check | Authority | Stage | Script | Switch |
|---|---|---|---|---|---|
| LG-00 | Pin assignment first, logical view. Every signal and interface in the logical design has a pin whose function supports it, and the pin table row says where that came from and whether a human or a second worker confirmed it. "Is it really that ADC channel, or are we guessing?" Then EL-01 and BD-01 for the electrical and physical views | configurator export, vendor pin data or the datasheet pin table, in that order of trust | ST4, ST5, ST6 | `sch_check.py pins`, `sch_check.py alloc` | always |
| LG-01 | Every functional requirement (FR-) maps to a block, and at the schematic checkpoint has evidence: a check that can fail, a DS- row result, or a review verdict | the user's requirements in `design/requirements.md` | ST4, ST6 | `table_check.py summary` | always |
| LG-02 | Every quality characteristic (QC-) has a named check or calculation and a result: cost, size, operating temperature range, supply range, current in each state, service life, and any standard the user named | the user; the calculations in `design/calcs/` | ST1, ST6 | none | always |
| LG-08 | No architecture change without the user. When the user states a preference, it is recorded with the default or earlier choice it replaces, and acted on only when the user agrees. A new answer that contradicts an earlier decision is flagged at once, and neither is changed until the user chooses. A recommendation that reverses an agreed figure says so in the same line | the user; `design/decisions.md` | all | none | always |
| LG-09 | Every interface is named with its exact variant and speed (for example classic or the faster variant of a bus), and each candidate part's own words confirm it supports that variant | interface specification, fetched; each part's datasheet | ST1, ST3 | none | always |
| LG-17 | Sold or not, where, and to whom, and what that switches on: emission and immunity classes, radio rules, product safety, substance rules, take-back and recycling, battery transport rules, and the marks the market needs. Each named regulation is fetched, not recalled. The "will it be sold" answer is asked again when the signs change, and a board-type switch kept off on a stated condition is tested again at every requirements change | the user; the published regulations for each market, fetched; a test lab if the user has one | first session, ST1 | none | always; more under Rechargeable, Radio, Mains, Sold |
| LG-20 | Right-sizing both ways: an under-specified part or block is a failure; a heavily over-specified one is a cost finding. A proposal to leave something out states each principle it rests on: add no capability nobody asked for; do not shift the work downstream (if removing a feature moves the work elsewhere, the feature is probably needed); of two circuits that do the same job, the simpler and cheaper; the end user's and the developer's experience. Where the principles pull apart, the user chooses, with each side set out | datasheets; requirements; the user | ST6 | none | always |
| LG-24 | Mechanical envelope known: size, enclosure drawing or 3D model, mounting, openings. If not known, the board shape is recorded as provisional, and the user is told before fabrication that ordering now risks paying twice | the user; the enclosure drawing | ST1, ST8 | none | always |
| LG-25 | Environment profile complete: every supply the board might see (nominal, lowest, highest, transients, reversed, hot-plugged, every system it could be plugged into); operating, storage and transport temperature; humidity and condensation; vibration and shock; altitude; water and dust. Each item answered with its source, or "does not apply" with a reason, and each limit a QC- | the user; the product standard for the market if sold, fetched | ST1 | none | always |
| LG-26 | Module definitions. The logical design ends in a set of modules, each one sub-sheet under a top sheet of boxes. `design/modules.csv`, `design/module-nets.csv`, `design/rails.csv` and `design/separate-nets.csv` agree with `design/modules.md` and with each other; there is exactly one sheet per module; every net that joins two or more sheets is a table net and joins only the modules listed for it | `design/modules.md` and its tables; the user | ST4, ST5, ST6 | `sch_check.py modules` | always |
| LG-27 | The requirements file is sound in structure: every item and every profile row has a source; IDs are unique and in order; every item marked to confirm and every open question is in the To confirm list; every decision that says it affects the file is cited in it. A fault of form fails in every run; a gap is listed, and fails from ST1 on | `design/requirements.md`; `design/decisions.md` | ST1, ST6 | `table_check.py requirements` | always |
| LG-28 | Each promise the requirements make is checked against each number it depends on at the corners of supply, temperature and tolerance, not only at nominal | `design/requirements.md`; datasheets; the calculations in `design/calcs/` | ST4, ST6 | `worstcase.py` | always |

## User, states and behaviour

| ID | What to check | Authority | Stage | Script | Switch |
|---|---|---|---|---|---|
| LG-03 | User journey (unbox, plug in, power up, connect or pair, use, fault, unplug, store): each step has the buttons, indicators, connectors, labels and access it needs. Derive what the user needs, not only what the brief lists | the user; `design/requirements.md` | ST4, ST5 | none | always |
| LG-04 | Does each user-visible function give the user the feedback they need? Are the buttons the user needs there? Can the user see and reach them where the board will sit (which end faces the user)? | the user | ST4, ST8 | none | always |
| LG-05 | Each misuse case (wrong supply, reversed supply, hot-plug, shorted output, wrong cable, wrong port, ESD from the user, water) has a required behaviour and the part that gives it. Each protective block carries one plain walk-through, step by step, of the failure it guards against. Each protective part is tested against the cases in EL-54 | the user; misuse clauses of the product standard if one applies, fetched; the datasheets of the parts that give the behaviour | ST1, ST4 | none | always |
| LG-06 | States: start-up, shutdown, sleep and wake, fault, removal. What each output does in each state. The sleep and wake strategy is decided, not left open | the user; the microcontroller datasheet's low-power and reset sections | ST4 | none | always |
| LG-07 | Non-obvious connections (a wake line to a second pin, a shared pin, a signal routed across the board) are put to the user as numbered decisions with their cost on the board | `design/decisions.md` | ST4, ST5 | none | always |
| LG-10 | Power tree and current budget per rail and per state (active, radio bursts, idle, sleep, off, shipping): peak, average and start-up current against each regulator's rating, with margin. The load on a rail or a driven net is summed across every sheet that touches it; the share of the budget used is shown after every block and flagged above a set level | supply-current tables in each load's datasheet; regulator datasheets | ST4, ST5 | `sch_check.py currents` (dividers and pulls), `sch_check.py netload`, `worstcase.py` | always; more under Battery |
| LG-11 | Safe state on firmware failure: for every output that drives something (a bus, motor, heater, relay, enable), its state on a hang, a reset and a brown-out, and which part guarantees it. For every output that can do harm: the driver's truth table with its inputs floating, the processor's pin states in reset, and whether the chosen reset stops a running timer output (a watchdog reset may not). A half-bridge gets a hardware interlock by default | datasheets (the driver's truth table, the processor's reset-state table); requirements | ST4, ST5 | `sch_check.py powerup` (fault column) | always; more under Motors, Microcontroller |
| LG-16 | Service life and duty cycle recorded: years of service, hours a day, power cycles, plug cycles, button presses, flash writes. The life calculations are EL-42 | the user | ST1 | none | always; more under Sold |
